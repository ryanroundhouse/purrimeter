# Host the multiplayer relay in Go over secure WebSockets

The agreed multiplayer model needs public game discovery, password admission, three-player membership, reconnect reservations, chat, and visible-state forwarding while each Godot client owns its simulation and saves. Use a single Go service with `github.com/coder/websocket`, a versioned JSON protocol, and Godot's `WebSocketPeer`; package it with Caddy and Docker Compose for VPS hosting. Keep live games in memory, consistent with the accepted server-restart behavior, while persisting server signing secrets and TLS material.

A headless Godot server would share the game language but is unnecessary for a relay that does not simulate combat. Go adds a language boundary in exchange for a separately deployable compiled service and an explicit protocol. WebSockets provide reliable ordered messages and straightforward HTTPS hosting; TCP can delay remote viewing under packet loss, an accepted engineering trade-off because local controls and combat do not depend on network round trips. Server authority applies to membership and permissions, not the legitimacy of personal progression.

Godot documents [third-party text/JSON communication and secure connections through WebSocketPeer](https://docs.godotengine.org/en/stable/classes/class_websocketpeer.html) and [the reliable TCP transport trade-off](https://docs.godotengine.org/en/stable/tutorials/networking/websocket.html). The selected Go library is [coder/websocket](https://github.com/coder/websocket). Caddy supports [automatic HTTPS](https://caddyserver.com/docs/automatic-https) and [WebSocket reverse proxying](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).
